# AI Project Setup

Набор правил, шаблонов и рабочих процессов, которые позволяют AI-агентам работать в репозитории структурированно и предсказуемо.

Проект не предоставляет CLI или runtime-код. Его продукт — договорённость: как агент ведёт себя в проекте, как документируется архитектура и как передаётся контекст между сессиями.

## Текущая цель

Создать минимальную, но рабочую основу для AI-агентного разработчика:

- `AGENTS.md` задаёт постоянные правила поведения агента в проекте.
- Шаблоны документации в `docs/` определяют, что и как нужно фиксировать.
- Специализированные workflows в `docs/workflows/` описывают процессы сопровождения документации.

## Структура репозитория

```
ai-project-setup/
├── AGENTS.md                                  # Постоянные правила агента
├── README.md                                  # Этот файл
├── install.sh                                 # Установщик файлов модели в целевой проект
└── docs/
    ├── ARCHITECTURE.md                        # Строгая документация текущей архитектуры
    ├── DECISIONS.md                           # Строгий реестр подтверждённых решений
    ├── HANDOFF.md                             # Рабочий буфер контекста между сессиями
    └── workflows/
        ├── handoff.md                         # Сопровождение рабочего буфера HANDOFF
        ├── permanent-docs-sync.md             # Продвижение подтверждённых кандидатов в постоянную документацию
        ├── architecture.md                    # Формат и evidence-правила ARCHITECTURE
        └── decision.md                        # Формат и source-правила DECISIONS
```

## `AGENTS.md`

Файл с постоянными правилами для AI-агентов, работающих в репозитории. Он определяет:

- что нужно сделать перед началом задачи;
- каковы правила реализации;
- как определяется завершённость задачи;
- общие принципы обслуживания документации;
- как работает автоматическая проверка HANDOFF;
- какая документация является источником истины.

Агент не должен менять код, не понимая контекста. `AGENTS.md` — договорённость, а не описание функциональности.

## Шаблоны документации

Файлы в `docs/` на текущем этапе представляют собой заготовки с заданной структурой разделов. Содержимое появится по мере развития проекта.

- **`docs/HANDOFF.md`** — рабочий буфер контекста между сессиями. Может быть немного «сырым», но должен оставаться полезным и фактически верным. Не является источником доказательств для постоянной документации.
- **`docs/ARCHITECTURE.md`** — строгий документ: описывает только фактическую текущую архитектуру. Каждое утверждение проверяется по фактическому состоянию проекта и подтверждённым проектным артефактам.
- **`docs/DECISIONS.md`** — строгий реестр: фиксирует только реально принятые решения с подтверждённым rationale. Рationale не выдумывается.

### Workflows документации

- **`docs/workflows/handoff.md`** — сопровождение HANDOFF после завершения существенной задачи. HANDOFF — единственный документ, который проверяется автоматически.
- **`docs/workflows/permanent-docs-sync.md`** — продвижение подтверждённых кандидатов из HANDOFF в ARCHITECTURE / DECISIONS. Вызывается **только явно** и никогда не запускается автоматически после задач.
- **`docs/workflows/architecture.md`** — формат разделов и evidence-правила ARCHITECTURE.
- **`docs/workflows/decision.md`** — формат записей и source-правила DECISIONS.

### Модель взаимодействия

```
development task
→ HANDOFF (рабочий буфер, фактически верный)
→ permanent-docs-sync (только явный вызов)
→ verify candidates against sources
→ ARCHITECTURE / DECISIONS (строгие, нормализованные)
```

HANDOFF = сигнал / кандидат.

Для ARCHITECTURE доказательством служит фактическое состояние проекта и подтверждённые проектные артефакты.

Для DECISIONS доказательством служит явно зафиксированный контекст решения и rationale.

ARCHITECTURE и DECISIONS = нормализованный результат.

Шаблоны не являются плейсхолдерами, которые нужно заполнить немедленно. Они становятся актуальны, когда проект обрастает архитектурой и принятыми решениями.

## Установка

`install.sh` копирует файлы модели (правила агента, шаблоны документации и workflows) в существующий целевой проект. Установщик безопасен: если хотя бы один файл уже существует, установка прерывается без изменений.

```
./install.sh <target-project-path>
```

## Scope MVP

На текущем этапе в scope входит:

- `AGENTS.md` с полным набором базовых правил;
- шаблоны `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, `docs/HANDOFF.md`;
- workflows: `docs/workflows/handoff.md`, `docs/workflows/permanent-docs-sync.md`, `docs/workflows/architecture.md`, `docs/workflows/decision.md`;
- установщик `install.sh`;
- этот `README.md`.

Не входит в scope MVP:

- CLI-интерфейс;
- vendor-specific файлы (`CLAUDE.md`, `GEMINI.md` и аналоги);
- skills и adapters;
- runtime-код.
